## 已接入能力

### Mercur 与社区交易

- Mercur `2.3.1` 作为交易核心，Medusa 运行时固定为 `2.18.0`。
- Mercur 使用独立 PostgreSQL 数据库和 Redis，不接触 ZITADEL 身份数据库。
- ZITADEL Token 自定义认证 Provider 已接入 Mercur，身份、租户和角色由 ZITADEL 统一控制。
- FFAX Node API 已提供分类、地区、自定义字段、需求、收藏、报价/还价、会话、未读通知、评价、举报、审核、封禁、推荐和推广状态。
- 插件数字商品授权与订单状态联动已经实现；真实资金扣款保持关闭，等待企业 KYC 和生产支付密钥。
- 未执行 Mercur 示例种子脚本，因此未部署示例管理员或示例商家账户。
- OpenClassify 仅作为公开功能参考，没有复制其源码、样式、迁移或素材。

### 微前端与可定制工作台

- `qiankun@2.10.16`：交易市场、社区、插件中心按路由独立加载。
- `react-grid-layout@2.2.4`：桌面/平板/手机布局、拖拽、缩放、编辑模式、恢复默认和服务端版本化保存。
- `golden-layout@2.6.0`：订单、物流、会话、文件和追踪等专业页面的标签、分屏、最大化、关闭与恢复。
- 微应用使用统一 `MicroAppContext` 获取即时 Token、租户、用户、角色、语言、主题、导航、通知和受控事件接口。
- 静态资源位于 `/workbench/microapps/<app>/`，没有使用 iframe。
- 布局 API 从 ZITADEL Token 读取可信租户和角色，不接受客户端提交可信 `tenantId`。

- FFAX 根前端审计仍有 2 个高风险上游项，来自旧 Svelte 4 / `svelte-gantt` 依赖链。
- Mercur 构建审计显示 20 个高风险上游依赖项；最终运行镜像审计显示 15 个高风险项。
- 未执行 `npm audit fix --force`，因为它会跨主要版本强制改写 Mercur/Medusa 依赖并可能破坏交易核心。应在独立升级分支中逐项替换或等待上游修复。
